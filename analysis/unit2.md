# Unit 2 Write-up: Airline Booking Schema

Theme: airline flight booking (passengers, flights, airports, bookings, flight routes).
Target: PostgreSQL 14+.

## The constraints table

| Foreign key | ON DELETE | Reason |
|---|---|---|
| `bookings.passenger_id` -> `passengers.passenger_id` | RESTRICT | A booking is a payment record, so a passenger who has bookings must not be deletable. |
| `bookings.flight_id` -> `flights.flight_id` | RESTRICT | A flight with sold tickets cannot disappear without orphaning or erasing what customers paid for. |
| `flight_routes.flight_id` -> `flights.flight_id` | CASCADE | Route stops describe a flight and mean nothing without it, so they go when the flight goes. |
| `flight_routes.airport_code` -> `airports.airport_code` | RESTRICT | An airport that a flight still stops at cannot be removed without breaking that flight's route. |

### Why each choice, in terms of real events

**`bookings.passenger_id`: RESTRICT.** The real event is a passenger asking to close their account, or staff cleaning up a duplicate profile. Under RESTRICT, PostgreSQL refuses to delete the passenger while any booking row points at them. That protects the finance and operations side: the airline still needs to know who held seat revenue for past and upcoming flights, for refunds, disputes, tax records and boarding checks. The alternative, CASCADE, would silently delete every booking the passenger ever made. Revenue history would shrink, a passenger with a ticket for tomorrow's flight would lose it with no warning, and nobody would be told. SET NULL is not available as a safe middle path because `passenger_id` is `NOT NULL`, and it should be: a booking with no passenger is meaningless. The cost of RESTRICT is that deletion requests need a deliberate process (cancel or archive the bookings first, or anonymize the passenger row), which is the right friction for personal and financial data.

**`bookings.flight_id`: RESTRICT.** The real event is operations removing a flight from the schedule, for example a route being discontinued or a flight number entered by mistake. If tickets have been sold, the people affected are the passengers holding those bookings and the customer service staff who must rebook or refund them. RESTRICT forces that to happen first: the delete fails until the bookings are dealt with. Under CASCADE, deleting the flight would erase every booking on it, and the airline would lose the record that it owes those customers money or a seat. The intended way to retire a flight is to set `flights.is_active` to `FALSE`, which stops new sales and keeps history intact. A hard delete should only succeed for a flight that never sold anything, such as one created by mistake, and RESTRICT gives exactly that behaviour.

**`flight_routes.flight_id`: CASCADE.** The real event is a flight being deleted, which by the rule above can only happen when it has no bookings. A route row is a pure description of the flight (stop 1 is Boston, stop 2 is London, and so on). It has no meaning, no payment attached and no customer attached once the flight is gone. Under RESTRICT, staff would have to delete every stop by hand before deleting the flight, and a half-finished cleanup would leave route stops hanging around for a flight that no longer exists. CASCADE makes the delete a single clean operation. The one thing affected is the schedule data itself, which is intended. This choice is safe only because of the RESTRICT on `bookings.flight_id`: customer-facing data blocks the delete first, so the cascade can only ever remove descriptive data.

**`flight_routes.airport_code`: RESTRICT.** The real event is an airport being removed from the reference table, for example because it was added by mistake or because it closed. The affected parties are the flights that still stop there: their routes would have a hole in them, or lose a stop entirely under CASCADE, and a flight might quietly become a different journey than the one passengers booked. Under RESTRICT, the delete fails and staff must reroute or retire the affected flights first, which makes the consequence visible. CASCADE is wrong here because the dependency points the opposite way from the flight case: the route row depends on the airport only as one of its attributes, and deleting a stop from a route is a change to the flight's service, not a cleanup of orphaned data. An airport closure is a business event that someone must decide on, not something the database should resolve on its own.

## The CHECK constraints

**`chk_flights_base_fair_nonneg` (`base_fair >= 0`).** It makes a flight with a negative base fare unstorable. Such a value could arise from a typo during data entry, a pricing job that subtracts a discount from the fare instead of applying it to the sale price, or an import where a sign gets flipped. Once stored, a negative base fare would flow into any report or booking logic that reads it, and could result in the airline paying customers to fly or in revenue totals that understate sales. The constraint allows zero deliberately, to permit promotional or fully subsidized flights, since the sentence "free" is a business decision and not a data error.

**`chk_bookings_fare_paid_nonneg` (`fare_paid >= 0`).** It makes a booking with a negative amount paid unstorable. This state could arise most plausibly when a developer models a refund by inserting a negative `fare_paid` row instead of recording it some other way, or when application code computes `fare_paid` as price minus discount and a large discount overshoots. Either way it would silently corrupt revenue sums: a `SUM(fare_paid)` would mix money received with money returned, with nothing in the row to tell them apart. Refunds are a different fact from a purchase and should be modeled separately (for example as their own table or a booking status), so this constraint pushes the design in that direction.

**`chk_airports_code_format` (`airport_code ~ '^[A-Z]{3}$'`).** It makes an airport code that is not exactly three uppercase letters unstorable. Because `airport_code` is the primary key and the target of `flight_routes.airport_code`, a malformed code would not just be a bad value; it would become a second, distinct identity for the same airport. Realistic ways to get there: a user or an import typing `bos` or `Bos` (which PostgreSQL treats as different from `BOS`), trailing whitespace from a spreadsheet export, or a four-letter ICAO code (such as `KBOS`) mixed into a table of three-letter IATA codes. The result would be duplicate airports that cannot be joined to each other, and routes that point at the wrong one. Note the limit of this check: it guarantees the format, not that the code belongs to a real airport.

**`chk_flight_routes_sequence_positive` (`sequence_number >= 1`).** It makes a route stop numbered zero or below unstorable. The sequence number gives the order of stops, so stop 1 is the origin and higher numbers follow. A zero or negative value could arise from application code that uses zero-based indexes (a loop counter starting at 0), from a bad import, or from a stop being given a negative number to push it "before" the first one. That would break any query that assumes the first stop is `sequence_number = 1`, for instance one that finds the origin airport, and would leave routes whose order different parts of the system read differently. This constraint does not prevent gaps (1, 2, 4) or require the numbers to be consecutive; it only fixes the starting point. Duplicate numbers on the same flight are already prevented by the composite primary key `(flight_id, sequence_number)`.
